Technical details

The record, and what it is not.

This page is the architecture, the comparison, and the limitations. The sales page is the short version. Nothing here is hidden from it; it is just no longer standing in front of the price.

Who it is for

Developers running long coding-agent sessions in OpenCode.

For people who want each new session, and each session after a compaction, to start from what was decided, done, failed and blocked. Claude Code, Codex, Muse, Cursor, Kiro and GitHub Copilot work too, through the bundled MCP server.

Who it is not for

  • A knowledge base or documentation search. It records what happens in sessions, not your documents.
  • Semantic or vector search over code. Use the structural tools or your editor.
  • A hosted or team service. Everything stays on one machine, in one repository.
  • A transcript store. It keeps the current state, not the conversation.

How it works

Code operations and persistent state, connected locally.

Host adapter

OpenCode uses the native plugin. Other compatible coding agents call the bundled MCP server. The adapter provides tool access and access to supported session histories.

Structural core + ast-grep

The shared structural core and bundled ast-grep provide AST and text search, bounded reads, and guarded preview/apply operations on project files.

State engine

A small Rust binary turns observed session activity into project facts and updates them when later events supersede earlier information.

Local state and capsule

Project facts stay local through .openstate/, which may be a directory, a symlink or a local pointer file. OpenCode adds the capsule at session start and after compaction; MCP clients request it on demand. openstate_why shows a fact’s provenance.

Known weaknesses

What the record does not cover.

  • It records only what passes through the host's events: messages, commands with their exit codes, file edits and git status. It does not see the model's reasoning, file contents, or work you do in your own terminal.
  • Decisions are recognised by wording. A message that gives a reason ("because", "since", "so that", "in order to", "due to") becomes a decision; a decision stated without one is recorded as a directive or objective, and a casual "because" can be recorded as a decision. openstate_close removes false ones.
  • A failure needs an exit code. A command whose tool reports no exit code is recorded as completed, not failed (it never counts as a passing test, though). Read-only commands such as cat, ls or grep are not recorded at all.
  • On hosts other than OpenCode the capsule is on demand: the agent has to call openstate_capsule (the MCP server's instructions tell it to).
  • One machine, one repository. There is no sync between machines or people.
  • No measurement yet shows fewer repeated failures. What OpenState guarantees is the record and its delivery to the agent; whether that changes your agent's behavior is for you to judge in your own sessions. Token cost per completed work item is measured and fell with adoption (see the evidence page).
  • The engine is closed source (the plugin, installer, skill and documentation are MIT).

The structural tools have their own costs — extra calls for a small edit, syntax matching rather than types — on the code tools page.

Principles

01

State, not story

A record of what is true now, compiled from events, not a summary written by a model.

02

Local only

No runtime network calls except license checks, no telemetry. State lives in your repository.

03

Deliberate persistence

State is written on checkpoint, when OpenCode closes, and when the engine’s input ends.
