Read the function, not the file.

A coding agent with only a file reader works in whole files: it reads the file to change one function, reads it again when the line numbers move, and edits text it matched by eye. OpenState’s structural tools let it search for a definition, read just that definition, and change it through a preview it can check before anything is written.

How the agent uses them

Find, read, preview, apply.

01 FIND

Search

openstate_ast_search for the name or the text. The answer is a list of places, not file contents.

02 READ

Read one unit

openstate_read_symbol for a definition, openstate_read_text_region for prose and configuration.

03 PREVIEW

See the change

The matching preview tool returns the planned change and an identity. It writes nothing.

04 APPLY

Write it once

The apply tool writes exactly what the preview showed, and refuses a second use of the same identity.

The skill and the MCP server’s instructions tell the agent this order. In OpenCode you can go further: installing with OPENSTATE_STRUCTURAL_TOOLS=enforce denies the built-in read, grep and edit tools so every read and edit goes through the structural tools.

What the write path guarantees

Refusal instead of damage.

  • Nothing is written by a preview. Only an apply writes, and only the change its preview showed.
  • Each preview applies once. A second apply of the same identity is refused as already_consumed.
  • A stale preview is refused, not forced. If the file changed so the previewed change no longer fits, the apply is refused as stale_files.
  • An ambiguous target is refused. When text matches more than once, the refusal lists every match.
  • A replacement must be one definition. A symbol replacement that does not parse as a single definition of the right kind is refused before anything is written, with the reason.
  • TypeScript and JavaScript exports stay intact. Replacing an exported function keeps its export keyword, and deleting one removes the keyword with it.

Known weaknesses

Where they cost more.

  • A small edit costs more calls. Search, preview and apply are three calls where a direct editor uses one. For a one-line change inside a long function, a text edit is cheaper than replacing the whole definition.
  • Searches are the heaviest read. A search with many matches can return several kilobytes; a language, a path or an exact name narrows it.
  • Matching is by syntax, not by type. References and renames match names in the syntax tree; they do not resolve types the way a compiler or language server does.
  • Completion cost fell with adoption (measured).
